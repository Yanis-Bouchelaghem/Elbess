# Marketplace MVP — Architecture Plan

## Context
New greenfield project (separate from universal_finder): a peer-to-peer secondhand marketplace app (same product category as Vinted). MVP features: auth (email/password + Google/Facebook), listing feed with filters, listing detail, create listing, buyer/seller chat with price offers, push notifications.

**Buying is an offer, not a button.** "Buy now" sends an offer at the asking price; the seller accepts, counters, or declines. Accepting sets the listing to `reserved` and is the end state — no payments, checkout, or shipping in the app.

## Decisions made
- **Mobile**: Expo / React Native (TypeScript, Android-first but cross-platform)
- **Backend**: Hono on Node, on a VPS behind **Caddy** (automatic HTTPS — no certbot needed)
- **Auth**: Better Auth with the Expo plugin, sessions stored in SecureStore
- **DB**: Postgres + Drizzle ORM (Better Auth has a first-class Drizzle adapter)
- **Photos**: S3-compatible bucket (Cloudflare R2), presigned-URL direct uploads
- **Payments**: none — accepting an offer reserves the item; the exchange happens outside the app
- **Chat**: in scope. Conversations, messages and offers live in Postgres alongside everything else — *not* Firebase/Firestore, because accepting an offer must flip `listings.status` in the same transaction as marking the offer accepted, which a second datastore cannot do
- **Realtime**: SSE (server→client) backed by Postgres `LISTEN/NOTIFY`; sending is a plain POST, so WebSockets buy nothing. Start with polling, swap transport later — the data model and endpoints are identical
- **Currency**: fixed to DZD, stored as integer minor units in `price_minor` (2 decimals: 2550 = 25.50 DZD)
- **Location**: dropped — no city field for now
- **Moderation**: out of scope (report button at most)
- **Repo**: pnpm monorepo

## Monorepo layout
```
apps/
  api/        # Hono + Better Auth + Drizzle
  mobile/     # Expo app (Expo Router)
packages/
  shared/     # zod schemas + types shared by both
```
The mobile app imports `AppType` from the API and uses `hono/client` (`hc<AppType>`) for a fully typed API client.

## Data model (Drizzle, Postgres)
- `user`, `session`, `account`, `verification` — generated by Better Auth CLI (`user.image` doubles as the avatar)
- `listings`: id (uuidv7), sellerId → user, title, description, category, condition (`new_with_tags` | `like_new` | `good` | `fair`), priceMinor, status (`active` | `reserved` | `sold`), reservedBy → user (`ON DELETE SET NULL`, unlike sellerId which cascades), reservedAt, createdAt, updatedAt, deletedAt
- `listing_photos`: id, listingId, objectKey, sortOrder (sortOrder 0 = cover)
- `conversations`: id, listingId, buyerId, sellerId, lastMessageAt, buyerLastReadAt, sellerLastReadAt — unique on (listingId, buyerId)
- `messages`: id, conversationId, senderId, kind (`text` | `offer` | `system`), body, priceMinor (offers only), offerStatus (`pending` | `accepted` | `declined` | `countered`), createdAt

Notes:
- `category` stays a plain `text` column, not an enum or FK table — the taxonomy is still provisional and changing it must not require a migration. Valid values are a zod enum in `packages/shared`, enforced at the HTTP boundary.
- Listings are **soft-deleted** (`deletedAt`). Hard deletion cascades photo rows away, destroying the `objectKey`s needed to clean up R2.
- `purchases` is gone — reservation is a side effect of accepting an offer.

## API surface (Hono)
- `ALL /api/auth/*` → `auth.handler` (Better Auth owns this subtree)
- `GET /api/listings?category=&condition=&minPrice=&maxPrice=&q=&cursor=` — public, cursor-paginated (category/condition are multi-select)
- `GET /api/listings/:id` — public, includes photos + seller
- `GET /api/users/:id/listings?cursor=` — public; seller profile, active + reserved by default
- `POST /api/listings` — authed; body validated with zod via `@hono/zod-validator`, schema lives in `packages/shared`
- `POST /api/listings/:id/photos/presign` — authed, owner-only; returns presigned PUT URL + objectKey
- `PATCH /api/listings/:id` / `DELETE` — authed, owner-only (DELETE is a soft delete)

Chat & offers:
- `GET /api/conversations` — authed; inbox list + unread counts
- `POST /api/conversations` — authed; find-or-create for (listingId, buyerId)
- `GET /api/conversations/:id/messages?cursor=` — authed, participants only
- `POST /api/conversations/:id/messages` — authed; `kind: "text" | "offer"`
- `POST /api/messages/:id/accept` — authed, seller only. **One transaction**, all of it or none:
  1. mark this offer `accepted`
  2. set listing `reserved` + `reservedBy` = buyer + `reservedAt` = now
  3. **auto-decline every other `pending` offer on the same listing**, across all conversations
  4. insert a system message in each affected conversation so losing buyers see why
  - Race guard: a seller can tap accept on two offers at once. Take a row lock (`SELECT … FOR UPDATE`) and re-check `status = 'active'` inside the transaction, or both offers win and the second silently overwrites `reservedBy`
- `POST /api/messages/:id/decline` / `counter` — authed, recipient only
- `POST /api/conversations/:id/read` — authed; moves the reader's `lastReadAt`
- `GET /api/conversations/:id/stream` — authed; SSE, fed by Postgres `LISTEN/NOTIFY`

Auth middleware sets `c.var.user` from `auth.api.getSession()`; applied to all mutating routes.

## Photo upload flow
1. App picks image (`expo-image-picker`), compresses client-side (`expo-image-manipulator`, ~1080p JPEG)
2. `POST .../photos/presign` → `{ url, objectKey }` (API uses `@aws-sdk/s3-request-presigner` against R2)
3. App PUTs bytes directly to R2 — VPS never handles image traffic
4. Photos served via R2 public bucket / custom domain

## Mobile app (Expo)
- Bottom tabs: Home, Sell (prominent center action), Inbox (unread badge), Profile
- Expo Router: `(auth)/login`, `(auth)/register`, `(tabs)/index` (feed), `listing/[id]`, `seller/[id]`, `sell/` (3-step wizard: photos → details → review), `inbox/`, `conversation/[id]`, `profile/`
- TanStack Query for server state; infinite query for the feed, seller listings, and messages
- Better Auth `expoClient` plugin: `authClient.signIn.social({ provider: "google" })`, cookie kept in SecureStore
- Filters sheet: category + condition (multi-select) + price range — all just query params
- One reusable empty / skeleton-loading / error trio, shared across every list screen

## Push notifications (last milestone)
- `expo-notifications` → store the Expo push token per user in a `push_tokens` table
- API sends via Expo's push service (`POST https://exp.host/--/api/v2/push/send`) on new message, new offer, and offer accepted/declined events
- Covers the case SSE cannot: the app is backgrounded, so the stream is closed
- Expo's service uses FCM under the hood on Android, so an FCM key is configured in EAS — Firebase as a delivery channel only, not as a datastore
- Requires an EAS build (not Expo Go) for Android push

## Deployment
- VPS: Node 22 + pnpm, API run under systemd (or pm2), Postgres on the same box to start
- Caddyfile: `api.yourapp.com { reverse_proxy localhost:3000 }` — TLS is automatic
- Mobile: **EAS Build (cloud)** — no Android Studio or Xcode needed locally; builds run on Expo's servers, triggered from WSL:
  - `eas build --platform android --profile preview` → installable APK for testing
  - `eas build --platform android --profile production` → AAB for the Play Store
  - Free tier ~30 builds/month is enough: rebuilds are only needed on native config changes, day-to-day JS/TS changes hot-reload through the dev client
  - iOS later: EAS builds it from WSL too (no Mac/Xcode), but signing requires an Apple Developer account ($99/yr)
  - Escape hatch if cloud queue annoys: `eas build --local` with just the Android SDK + JDK in WSL (full Android Studio never required)
  - Google OAuth needs the SHA-1 fingerprint of the EAS keystore registered in Google Cloud Console

## Verification
- Each milestone is user-testable: curl the API first, then run the Expo dev client against the deployed VPS API
- End-to-end check: register → create listing with photos on device A → find via filters on device B → send an offer → device A accepts → listing shows `reserved` on both, buyer sees the system message (later: gets a push)

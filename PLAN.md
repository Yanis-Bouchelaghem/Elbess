# Marketplace MVP — Architecture Plan

## Context
New greenfield project (separate from universal_finder): a mobile marketplace app. MVP features: auth (email/password + Google/Facebook), listing feed with filters, listing detail (price, location, photos, contact), create listing, "buy" = reserve/mark-sold (no real payments), push notifications later. Chat is out of scope for iteration 1.

## Decisions made
- **Mobile**: Expo / React Native (TypeScript, Android-first but cross-platform)
- **Backend**: Hono on Node, on a VPS behind **Caddy** (automatic HTTPS — no certbot needed)
- **Auth**: Better Auth with the Expo plugin, sessions stored in SecureStore
- **DB**: Postgres + Drizzle ORM (Better Auth has a first-class Drizzle adapter)
- **Photos**: S3-compatible bucket (Cloudflare R2), presigned-URL direct uploads
- **Payments**: none — buy button reserves the item and notifies the seller
- **Location**: city as text/dropdown, no geo queries
- **Moderation**: out of scope (report button at most)
- **Repo**: pnpm monorepo

## Monorepo layout
```
apps/
  api/        # Hono + Better Auth + Drizzle
  mobile/     # Expo app (Expo Router)
packages/
  shared/     # zod schemas + types shared by both
```
The mobile app imports `AppType` from the API and uses `hono/client` (`hc<AppType>`) for a fully typed API client.

## Data model (Drizzle, Postgres)
- `user`, `session`, `account`, `verification` — generated by Better Auth CLI
- `listings`: id, sellerId → user, title, description, price (integer cents), city, category, contactPhone/contactEmail, status (`active` | `reserved` | `sold`), createdAt
- `listing_photos`: id, listingId, objectKey, sortOrder
- `purchases` (reservation records): id, listingId, buyerId, createdAt

## API surface (Hono)
- `ALL /api/auth/*` → `auth.handler` (Better Auth owns this subtree)
- `GET /api/listings?category=&city=&minPrice=&maxPrice=&cursor=` — public, cursor-paginated
- `GET /api/listings/:id` — public, includes photos + seller contact
- `POST /api/listings` — authed; body validated with zod via `@hono/zod-validator`, schema lives in `packages/shared`
- `POST /api/listings/:id/photos/presign` — authed, owner-only; returns presigned PUT URL + objectKey
- `POST /api/listings/:id/buy` — authed; transaction: check status=active → set reserved → insert purchase → (later) push to seller
- `PATCH /api/listings/:id` / `DELETE` — authed, owner-only

Auth middleware sets `c.var.user` from `auth.api.getSession()`; applied to all mutating routes.

## Photo upload flow
1. App picks image (`expo-image-picker`), compresses client-side (`expo-image-manipulator`, ~1080p JPEG)
2. `POST .../photos/presign` → `{ url, objectKey }` (API uses `@aws-sdk/s3-request-presigner` against R2)
3. App PUTs bytes directly to R2 — VPS never handles image traffic
4. Photos served via R2 public bucket / custom domain

## Mobile app (Expo)
- Expo Router: `(auth)/login`, `(tabs)/index` (feed), `listing/[id]`, `sell.tsx`
- TanStack Query for server state; infinite query for the feed
- Better Auth `expoClient` plugin: `authClient.signIn.social({ provider: "google" })`, cookie kept in SecureStore
- Filters: category chips + price min/max + city — all just query params

## Push notifications (last milestone)
- `expo-notifications` → store the Expo push token per user in a `push_tokens` table
- API sends via Expo's push service (`POST https://exp.host/--/api/v2/push/send`) on buy/reserve events
- Requires an EAS build (not Expo Go) for Android push

## Deployment
- VPS: Node 22 + pnpm, API run under systemd (or pm2), Postgres on the same box to start
- Caddyfile: `api.yourapp.com { reverse_proxy localhost:3000 }` — TLS is automatic
- Mobile: **EAS Build (cloud)** — no Android Studio or Xcode needed locally; builds run on Expo's servers, triggered from WSL:
  - `eas build --platform android --profile preview` → installable APK for testing
  - `eas build --platform android --profile production` → AAB for the Play Store
  - Free tier ~30 builds/month is enough: rebuilds are only needed on native config changes, day-to-day JS/TS changes hot-reload through the dev client
  - iOS later: EAS builds it from WSL too (no Mac/Xcode), but signing requires an Apple Developer account ($99/yr)
  - Escape hatch if cloud queue annoys: `eas build --local` with just the Android SDK + JDK in WSL (full Android Studio never required)
  - Google OAuth needs the SHA-1 fingerprint of the EAS keystore registered in Google Cloud Console

## Build order (milestones)
1. Monorepo scaffold + Hono hello-world + Drizzle/Postgres + Better Auth email/password working from a curl
2. Expo app: login/register screens against the API
3. Listings CRUD + feed with filters + detail screen (no photos yet)
4. Photo presign/upload/display
5. Buy/reserve flow
6. Google (then Facebook) OAuth via EAS build
7. Push notifications

## Verification
- Each milestone is user-testable: curl the API first, then run the Expo dev client against the deployed VPS API
- End-to-end check: register → create listing with photos on device A → find via filters, reserve on device B → seller sees status change (later: gets a push)
